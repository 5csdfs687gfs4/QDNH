# Pantalla inicial sin señal recibida

La extensión `screen-snapshot-v1` del control compartido añade `ScreenSnapshotRequest=29` (`RequestId`) y `ScreenSnapshotState=30` (`RequestId`, `Width=128`, `Height=64`, `Data` base64, `CapturedAtUtc` ISO UTC, `Reason`). Sólo se atiende tras la autenticación y el Hello del canal de control; también puede solicitarla un observador sin adquirir control ni TX. Los clientes anteriores no reciben mensajes nuevos espontáneos.

QDNH genera exclusivamente el comando de lectura del framebuffer que ya admite el firmware Quansheng Dock: `0x0803`, timestamp cero, encuadrado y protegido por el XOR/CRC existentes. No simula teclas, cambia frecuencia, habilita PTT ni admite comandos arbitrarios en esta petición. La respuesta del firmware es `EF + 1024 bytes`, ocho páginas verticales de 128 columnas. El servidor retira esos bytes del flujo serie semántico de los clientes anteriores y entrega el mapa sólo por el control de los solicitantes.

Las peticiones simultáneas comparten una captura; hay como máximo 64 solicitantes, una lectura pendiente y un búfer fijo de 1024 bytes. Cada sesión puede pedir una vez por segundo; la caché se reutiliza sólo durante 500 ms y se invalida con tráfico UART ordinario o comandos CAT. El timeout de respuesta es de tres segundos (`no-data`), pero no cancela una lectura ya enviada al firmware: se mantiene su cuarentena sin ventana temporal hasta drenar `EF + 1024 bytes` o restablecer UART. Eso incluye respuestas cuyo primer EF llega mucho después del timeout y solicitantes que ya se desconectaron. Mientras se espera EF, el tráfico UI/binario ordinario continúa; no se emite una segunda consulta que pudiera descorrelacionar respuestas. Si un firmware no responde, sólo la función de captura queda ocupada hasta recuperar UART, en lugar de arriesgar corrupción del flujo de los clientes anteriores. No se interpreta un EF dentro de paquetes UI o binarios como un nuevo mapa; el tipo UI 6 usa su byte final como batería, no como longitud.

La lectura comparte el cerrojo del arbitraje de TX y las escrituras serie. Se devuelve `busy` durante TX, barrido conocido o los primeros tres segundos de estabilización. El barrido se reconoce en comandos autorizados `0808`/`0809` con CRC válido y también en respuestas espontáneas `0908`, incluidas las que llegan después de reiniciar el servidor. La pérdida UART conserva conservadoramente un barrido conocido hasta recibir un comando autorizado que lo termine; ninguna consulta debe terminar un barrido por su cuenta. La identificación de barridos depende del protocolo de firmware: un estado no reportado externamente no puede deducirse perfectamente.

Para usar esta extensión debe actualizarse QDNH antes de QDockX. En un servidor compartido anterior, el cliente no debe enviar una lectura raw por el canal serie: su difusión a clientes antiguos podría confundirse con paquetes UI. La consulta directa queda para los modos tradicional/USB que la implementación cliente pueda validar separadamente. Esta extensión no actualiza firmware ni altera sus límites; durante un barrido o TX se conserva la vista existente y se reintenta después de liberar la operación.

Validación aislada: pruebas de encuadrado/CRC, fragmentación, UI y cuerpos binarios con EF, coalescencia, caché, timeout y drenaje tardío/parcial, observadores, sockets reemplazados, guardas TX/barrido y estabilización. No utiliza una radio ni transmite RF.
